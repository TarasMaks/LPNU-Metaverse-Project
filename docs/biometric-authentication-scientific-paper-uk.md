## Анотація

Дана робота присвячена розробці та аналізу комплексної системи біометричної аутентифікації, інтегрованої з технологіями Web3 та децентралізованої ідентичності (DID). Система реалізує багатофакторну аутентифікацію (MFA), що поєднує розпізнавання облич, перевірку живості зображення, цифрові підписи гаманців та політики управління доступом. Архітектура системи забезпечує захист біометричних даних через шифрування на рівні зберігання (AES-256-GCM) та реєстрацію зобов'язань (commitment) на блокчейні без збереження сирих біометричних шаблонів. Проведена оцінка показує, що система забезпечує достатній рівень безпеки для застосування у метаверс-екосистемах при збереженні приватності користувачів та відповідності до регуляторних вимог (GDPR). Робота описує принципи роботи системи, ключові компоненти, криптографічні механізми та результати тестування.

**Ключові слова:** біометрична аутентифікація, розпізнавання облич, Web3, децентралізована ідентичність, багатофакторна аутентифікація, блокчейн, криптографія, управління доступом, метаверс, приватність даних

## 1. Вступ

### 1.1 Актуальність проблеми

Розвиток метаверс-технологій та децентралізованих застосунків (dApps) створює нові виклики для систем автентифікації та контролю доступу. На відміну від традиційних централізованих систем, Web3-додатки повинні забезпечити:

1. **Децентралізовану ідентичність** — користувачі контролюють власну цифрову ідентичність без залежності від єдиного постачальника послуг;
2. **Криптографічну верифікацію** — можливість перевірити автентичність дій користувача за допомогою математичних гарантій;
3. **Прозорість та аудит** — всі критичні дії записуються в незмінному форматі;
4. **Захист біометричних даних** — високочутливі біометричні інформація повинна захищатися от несанкціонованого доступу та зберігатися приватно.

Традиційні методи контролю доступу (паролі, OTP, простий 2FA) недостатні для забезпечення безпеки високовартісних операцій у метаверсі (фінансові трансакції, передача активів, управління цифровою власністю).

## 2. Обзір пов'язаних робіт

### 2.1 Біометрична аутентифікація

Біометрична аутентифікація поділяється на кілька категорій:
- **Біометрія облика** — розпізнавання за рисами обличчя (найпоширеніша у мобільних пристроях)
- **Біометрія відбитків пальців** — аналіз унікальних ліній на пальцях
- **Біометрія райдужки ока** — сканування райдужки ока
- **Голосова біометрія** — розпізнавання за голосом
- **Біометрія поведінки** — аналіз поведінки користувача (клацання, жести)

У світі дедалі більше використовується розпізнавання облиця завдяки удосконаленню нейромережевих моделей та зменшенню вартості обладнання [[1]].

### 2.2 Запобігання атакам на біометричні системи

Критичним аспектом біометричної аутентифікації є запобігання атакам подання (presentation attacks):
- **Фото атаки** — показ фотографії обличчя дійсної людини
- **Відеоатаки** — показ відео чи екрану з изображением обличчя
- **Маскові атаки** — використання маски, 3D-моделі обличчя
- **Лицьові трансформації** — косметика, окуляри, борода

Перевірка живості зображення (liveness detection) є важливим компонентом будь-якої виробничої системи біометрії.

Існує два підходи до перевірки живості:
1. **Активна перевірка живості** — просит користувача виконати дію (посміхнутися, кивнути, повернути голову)
2. **Пасивна перевірка живості** — аналізує статичне зображення на наявність ознак атаки

Система, описана в даній роботі, реалізує гібридний підхід із використанням легких паралельних перевірок.

### 2.3 Децентралізована ідентичність (DID)

Децентралізована ідентичність — це стандарт W3C, що дозволяє користувачам контролювати власну цифрову ідентичність без залежності від централізованого провайдера [[2]]:

- **DID** — унікальний ідентифікатор, контрольований користувачем
- **DID документ** — набір публічних ключів та точок контакту, пов'язаних з DID
- **Верифіковані облікові дані (VC)** — подписані затвердження про властивості DID

Розповсюджені схеми DIDs:
- `did:key:` — зберігає публічний ключ у самому DID
- `did:web:` — розташований на вебсайті
- `did:ethr:` — засновано на Ethereum адресі
- `did:sol:` — засновано на адресі Solana

### 2.4 Web3 та безпека розподілених застосунків

Web3-додатки мають унікальні вимоги безпеки:
- Криптографічна верифікація всіх операцій
- Незмінні журнали аудиту (blockchain)
- Самостійне управління ключами користувачем
- Відсутність традиційних центрів довіри

Стандарти OpenID Connect та SAML, розроблені для централізованої аутентифікації, менш придатні для децентралізованих систем [[3]].

### 2.5 Багатофакторна аутентифікація (MFA)

MFA поєднує кілька незалежних факторів:
- **Знання (Something you know)** — пароль, PIN, відповідь на питання
- **Володіння (Something you have)** — апаратний токен, смартфон, гаманець
- **Притаманність (Something you are)** — біометрія, ДНК
- **Місцезнаходження (Somewhere you are)** — GPS координати, IP адреса
- **Часові фактори** — часова синхронізація, час дня

Дана система реалізує MFA через поєднання цифрового підпису гаманця, біометричної верифікації та атестації пристрою.

### 2.6 Блокчейн для реєстрації біометричних даних

Ключова проблема зберігання біометричних даних — конфіденційність та незмінність реєстрів. Блокчейн дозволяє:
- Зберігати хеші зобов'язань (commitments) в незмінному форматі
- Запобігти несанкціонованій зміні записів
- Забезпечити прозорість без розкриття сирих даних

На блокчейні зберігаються лише хеші зобов'язань, а не самі біометричні шаблони [[4]].

### 3.2 Основні модулі системи

#### 3.2.1 Модуль розпізнавання облиця (DeepFace)

**Розташування:** `app/deepface_adapter.py`

Обгортка навколо бібліотеки DeepFace для:
- Витягування вкладень облиця (embeddings) розмірності 128D
- Порівняння двох облиць (1-до-1 відповідність)
- Перевірки живості зображення

**Поддержуемі моделі:**
- ArcFace (за замовчуванням, точність 99.8%)
- VGGFace2, Facenet512, OpenFace та інші

**Алгоритми детектування облиця:**
- RetinaFace (за замовчуванням, швидкий та точний)
- MTCNN, FastMTCNN, OpenCV та інші

**Метрики відстані:**
- Косинусна подібність (за замовчуванням)
- Евклідова відстань
- L2-норма

#### 3.2.2 Перевірка живості (Liveness Detection)

**Розташування:** `app/deepface_adapter.py` функція `check_liveness()`

Система реалізує три паралельні перевірки:

**1. Виявлення розмиття (Blur Detection)**
- Метод: дисперсія оператора Лапласа
- Ідея: нечіткі зображення та фотографії мають низьку дисперсію
- Формула: `σ² = E[(I ★ ∇²I)²]`
- Параметр: `liveness_blur_threshold` (за замовчуванням: 100.0)

**2. Перевірка розміру облиця (Face-to-Image Ratio)**
- Метод: обчислення відсотка площі облиця в зображенні
- Ідея: справжнє обличчя займає суттєву частину кадру
- Формула: `ratio = (face_bbox_area / image_area) * 100`
- Параметр: `liveness_min_face_ratio` (за замовчуванням: 5%)

**3. Аналіз діапазону кольорів (Colour Range Analysis)**
- Метод: стандартне відхилення RGB каналів
- Ідея: екрани та друковані зображення мають стиснений діапазон
- Формула: `σ_R, σ_G, σ_B` < 15.0
- Виявляє: лицьові маски, 3D-моделі, екран-атаки

**Результат:** Масив стану перевірок (`checks`) та причини невдачі (`reasons`)

#### 3.2.3 Модуль децентралізованої ідентичності (DID)

**Розташування:** `app/did.py`

**Схема DID:** `did:key:`

Генерація DID на основі ECDSA P-256 публічного ключа:
1. Генерується ECDSA пара ключів (secp256r1)
2. Публічний ключ кодується у стиснене X962 formato
3. Ключ базується на base64url та префіксується з `z6Mk` (для X25519 або secp256r1)
4. Повний DID: `did:key:z6Mk...`

**Адреса гаманця (Wallet Address):** Дорівнює Ethereum-адресі, обчисленій як Keccak-256(публічний_ключ)

**Документ DID:**
```python
@dataclass
class DIDDocument:
    did: str              # e.g., "did:key:z6MkhaXgBZD..."
    public_key_pem: str   # PEM-формат публічного ключа
    private_key_pem: str  # PEM-формат приватного ключа
    wallet_address: str   # Ethereum-style адреса (0x...)
```

#### 3.2.4 Модуль верифікованих облікових даних (VC)

**Розташування:** `app/vc.py`

Верифіковані облікові дані — це цифрово підписані затвердження про властивості суб'єкта.

**Формат:** JWT (JSON Web Token) із перевіреними полями

**Структура VC JWT:**
```json
{
  "iss": "did:key:biometric-identity-service",
  "sub": "did:key:{user_did}",
  "jti": "urn:uuid:{uuid}",
  "iat": {timestamp},
  "exp": {timestamp + 600},
  "vc": {
    "type": ["VerifiableCredential", "BiometricAssurance"],
    "credentialSubject": {
      "assuranceLevel": 2,
      "biometricMethod": "face",
      "nonce": "{challenge_nonce}"
    }
  }
}
```

**Рівні впевненості (Assurance Levels):**
- **Рівень 1:** Володіння гаманцем (цифровий підпис)
- **Рівень 2:** Володіння + біометричний доказ
- **Рівень 3:** Рівень 2 + атестація пристрою
- **Рівень 4:** Рівень 3 + позабережне підтвердження (OOB)

### 3.3 Процес реєстрації (Enrollment)

**Розташування:** `app/routers/enrollment.py`

Реєстрація біометричних даних користувача складається з двох фаз:

#### Фаза 1: Ініціація реєстрації

**Запит:** `POST /v1/enroll/start`
```json
{
  "user_id": "user@example.com",
  "version": "v1"
}
```

**Відповідь:**
```json
{
  "challenge": "a1b2c3d4e5f6g7h8",
  "salt": "x1y2z3w4",
  "version": "v1"
}
```

**Логіка:**
1. Генерується випадковий виклик (challenge) 8 байт
2. Генерується випадкова сіль (salt) 4 байти
3. Зберігається `DBEnrollmentChallenge` з TTL (за замовчуванням: 300 сек)

#### Фаза 2: Завершення реєстрації

**Запит:** `POST /v1/enroll/finish`
```json
{
  "user_id": "user@example.com",
  "template_data": "base64_encoded_embedding",
  "salt": "x1y2z3w4",
  "version": "v1",
  "storage_uri": "ipfs://QmXxxx or s3://...",
  "challenge": "a1b2c3d4e5f6g7h8"
}
```

**Логіка обробки:**
1. **Валідація виклику:** Перевіряється, що challenge існує і TTL не сплив
2. **Шифрування шаблону:**
   - Алгоритм: AES-256-GCM
   - Ключ: Похідне від master_key через SHA256
   - Результат: `nonce || tag || ciphertext` у Base64
3. **Обчислення зобов'язання (Commitment):**
   ```
   commitment = SHA256(encrypted_template_b64 || salt || version)
   ```
4. **Зберігання у БД:** `DBBiometricTemplate` з полями:
   - `user_id` — унікальний ідентифікатор користувача
   - `commitment` — хеш на блокчейні
   - `encrypted_template` — шифровані дані
   - `storage_uri` — URI позабережної сховищі
   - `status` — "active"

5. **Реєстрація на блокчейні (best-effort):**
   ```
   BiometricCommitmentRegistry.storeCommitment(
     user_id,
     commitment,
     version,
     storage_uri
   )
   ```

**Відповідь:**
```json
{
  "commitment": "abc123...hash...xyz",
  "storage_uri": "ipfs://QmXxxx",
  "version": "v1",
  "blockchain_tx": "0x123abc... or null"
}
```

### 3.4 Процес аутентифікації

**Розташування:** `app/routers/auth.py`

Аутентифікація складається з трьох кроків:

#### Крок 1: Отримання виклику (Challenge Phase)

**Запит:** `POST /v1/auth/challenge`
```json
{
  "user_id": "user@example.com"
}
```

**Логіка:**
1. Перевіряється, що користувач має активний біометричний шаблон
2. Генерується випадковий nonce (8 байт)
3. Зберігається `DBAuthChallenge` з TTL (300 сек)
4. Формується повідомлення виклику: `"authenticate:{user_id}:{nonce}"`

**Відповідь:**
```json
{
  "nonce": "f1e2d3c4b5a6g7h8",
  "challenge_message": "authenticate:user@example.com:f1e2d3c4b5a6g7h8"
}
```

#### Крок 2 та 3: Верифікація (Verification Phase)

**Запит:** `POST /v1/auth/verify`
```json
{
  "user_id": "user@example.com",
  "did": "did:key:z6Mk...",
  "nonce": "f1e2d3c4b5a6g7h8",
  "desired_level": 2,
  "template_data": "base64_probe_embedding",
  "wallet_signature": "base64_ecdsa_signature"
}
```

**Логіка верифікації:**

**1. Валідація nonce:**
- Отримується `DBAuthChallenge` за nonce
- Перевіряється наявність та TTL
- Nonce помічається як витрачений

**2. Біометричне порівняння (якщо probe надано):**
- Отримується зашифрований шаблон з БД
- Дешифрується за допомогою master_key: `decrypt_template(encrypted_blob, key)`
- Обидва вкладення аналізуються як JSON масиви
- Обчислюється косинусна подібність:
  ```
  similarity = (probe · template) / (||probe|| · ||template||)
  ```
- Верифікація: `similarity >= (1.0 - face_match_threshold)`
- За замовчуванням: `threshold = 0.40`, тому потрібна `similarity >= 0.60`

**3. Верифікація цифрового підпису (якщо наданий):**
- Отримується публічний ключ зі структури DID
- Верифікується підпис ECDSA-SHA256:
  ```
  verify_signature(public_key, challenge_message, signature)
  ```
- Для нашої системи: ECDSA P-256 (secp256r1)

**4. Видача Верифікованої облікової даних (VC):**
- Якщо `desired_level > 1` без біометричного доказу → відхилення
- Створюється JWT з payload:
  ```json
  {
    "iss": "did:key:biometric-identity-service",
    "sub": "{user_did}",
    "jti": "urn:uuid:{uuid}",
    "iat": {timestamp},
    "exp": {timestamp + 600},
    "vc": {
      "type": ["VerifiableCredential", "BiometricAssurance"],
      "credentialSubject": {
        "assuranceLevel": {level},
        "biometricMethod": "face",
        "nonce": "{nonce}"
      }
    }
  }
  ```
- Підпис: HS256 з `vc_signing_key` (в продакшені — асиметричний)
- Зберігається у БД: `DBVerifiableCredential`

**Відповідь:**
```json
{
  "vc_jwt": "eyJhbGc...",
  "vc_did": "did:key:z6Mk...",
  "level": 2,
  "expires_at": 1739123456,
  "biometric_verified": true,
  "liveness_passed": true
}
```

**Розташування:** `app/policy.py`, `app/routers/access.py`

Система реалізує нещодавно-вибудовану архітектуру контролю доступу з політиками на основі ролей та рівнів.

## 4. Криптографічні механізми

### 4.1 Шифрування шаблонів

**Алгоритм:** AES-256-GCM (Advanced Encryption Standard, 256-bit key, Galois/Counter Mode)

**Характеристики:**
- **Розмір ключа:** 256 біт (32 байти)
- **Режим:** GCM (забезпечує автентичність та конфіденційність)
- **Розмір nonce:** 12 байт (96 біт) — рекомендується для GCM
- **Розмір тегу автентичності:** 16 байт (128 біт)

**Процес шифрування:**
```
plaintext = embedding_bytes
key = SHA256(master_key_string)  [32 bytes]
nonce = random(12)               [12 bytes]
(ciphertext, tag) = AES-256-GCM(key, nonce, plaintext)
encrypted_blob = base64(nonce || tag || ciphertext)
```

**Процес дешифрування:**
```
encrypted_blob_bytes = base64_decode(encrypted_blob)
nonce = encrypted_blob_bytes[0:12]
tag = encrypted_blob_bytes[12:28]
ciphertext = encrypted_blob_bytes[28:]
key = SHA256(master_key_string)
plaintext = AES-256-GCM-decrypt(key, nonce, ciphertext, tag)
```

**Переваги GCM:**
- Забезпечує конфіденційність (зашифрування)
- Забезпечує автентичність (тег)
- Паралелізуємо (ефективна реалізація)
- Стандартизований (NIST)

### 4.2 Хешування зобов'язань

**Алгоритм:** SHA-256

**Формула:**
```
commitment = SHA256(encrypted_template_base64 || salt || version)
```

**Дизайн:**
- Зобов'язання не потребує ключа (публічний хеш)
- Дозволяє верифікувати цілісність без розкриття даних
- Може бути записано на блокчейні для прозорості

**Приклад:**
```
encrypted_template_b64 = "AgMDBAUGBwgJCgsMDQ4PEBESExQVFhcYGRobHBs..."
salt = "x1y2z3w4"
version = "v1"
commitment = SHA256("AgMDBAUGBwgJCgsMDQ4PEBESExQVFhcYGRobHBs...x1y2z3w4v1")
          = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
```

### 4.3 Цифрові підписи

**Алгоритм:** ECDSA з P-256 (secp256r1) та SHA-256

**Характеристики:**
- **Крива:** P-256 (NIST, широко підтримується)
- **Розмір ключа:** 256 біт (32 байти)
- **Хеш:** SHA-256
- **Формат підпису:** (r, s) — два 32-байтні значення

**Процес підпису:**
```
message = b"authenticate:user@example.com:f1e2d3c4b5a6g7h8"
hash = SHA256(message)
(r, s) = ECDSA_sign(private_key, hash)
signature_bytes = r || s                [64 bytes]
signature_base64 = base64(signature_bytes)
```

**Процес верифікації:**
```
signature_bytes = base64_decode(signature_base64)
r = signature_bytes[0:32]
s = signature_bytes[32:64]
hash = SHA256(message)
is_valid = ECDSA_verify(public_key, hash, (r, s))
```

**Безпека ECDSA:**
- Математично еквівалентна 256-бітному симетричному захисту
- Квантово-уразливий (для квантових комп'ютерів)
- Потребує якісної випадковості under the hood (система використовує `secrets` модуль Python)

### 4.4 Генерація nonce та ключів

**Функція:** `secrets.token_hex()` (криптографічно безпечна генерація)

**Властивості:**
- Базується на операційній системі генератору випадкових чисел (`/dev/urandom` на Unix)
- Непередбачувана (неможна угадати)
- Незалежна від попередніх значень

**Приклад генерації:**
```python
challenge = secrets.token_hex(8)   # 8 bytes = 16 hex chars
nonce = secrets.token_hex(8)       # 8 bytes = 16 hex chars
salt = secrets.token_hex(4)        # 4 bytes = 8 hex chars
```

## 5. Аспекти безпеки та приватності

### 5.1 Захист біометричних даних

#### 5.1.1 Шифрування на рівні зберігання

- Всі біометричні шаблони зберігаються в зашифрованому форматі (AES-256-GCM)
- Сирі біометричні дані ніколи не зберігаються в текстовому форматі
- Ключ шифрування отримується від master_key через хешування SHA-256

#### 5.1.2 Розділення даних

- **На серверу:** Зберігаються лише зашифровані шаблони та хеші зобов'язань
- **На блокчейні:** Зберігаються хеші зобов'язань (зустрічаються лише хеші, не самі дані)
- **У позабережній сховищі:** Можуть зберігатися оригінальні або зашифровані вкладення за політикою користувача

#### 5.1.3 Невідворотність

Рівень невідворотності біометричних даних дуже високий, оскільки:
- Хаші SHA-256 непрактично інвертуються
- Вкладення з DeepFace розроблені як невідворотні функції
- Запис на блокчейні унеможливлює видалення історичних даних

### 5.2 Запобігання повторним атакам (Replay Protection)

#### 5.2.1 Одноразові вики (Nonce)

- Кожен виклик (`challenge`) є одноразовим та має TTL (300 сек)
- Використаний виклик записується в БД та більше не приймається
- Nonce включається в VC для запобігання повторним використанням VC

#### 5.2.2 Часові мітки

- Усім VC встановлюються часові мітки видачі (`iat`) та закінчення (`exp`)
- Система перевіряє, що VC не просрочена перед її використанням

### 5.3 Атаки на біометричні системи

#### 5.3.1 Атаки подання (Presentation Attacks)

**Виклики:**
- Фото-атаки: показ фотографії або екрану
- Маскові атаки: использование маски чи 3D-моделі
- Лицьові трансформації: косметика, окуляри

**Запобігання (в системі реалізовано):**
1. **Виявлення розмиття:** Низька дисперсія Лапласа для нечітких зображень
2. **Перевірка розміру облиця:** Малий відсоток облиця вказує на фото-атаку
3. **Аналіз діапазону кольорів:** Екрани мають стиснений діапазон RGB

**Обмеження:**
- На рівні PoC легкі перевірки замість складних ML-моделей
- В виробництві рекомендується використовувати спеціалізовані моделі (напр., MobileNetV2 для liveness)

#### 5.3.2 Атаки на базу даних

**Загроза:** Компромісація БД та викривлення зашифрованих шаблонів

**Запобігання:**
- Шифрування на рівні БД
- Периметровий контроль доступу
- Аудит всіх операцій БД (future enhancement)
- Резервні копії з шифруванням

### 5.4 Управління ключами

#### 5.4.1 Master Key

**Критичність:** Найвищий рівень

**Поточна реалізація:** Зберігається як рядок в `.env` файлі

**Проблеми:**
- `.env` файл незащищений в системі розробки
- Одна точка відмови

**Рекомендації для продакшену:**
- Зберігати в системі управління секретами (AWS Secrets Manager, HashiCorp Vault)
- Ротація ключів на регулярній основі
- Кілька ключів для різних фаз (поточний, попередній)
- Hardware Security Module (HSM) для критичних операцій

#### 5.4.2 VC Signing Key

**Поточна реалізація:** HS256 з симетричним ключем

**Проблеми:**
- Симетричний ключ позбавляє можливості незалежної верифікації
- Вимагає поширення ключа іншим сервісам

**Рекомендації для продакшену:**
- Перейти на ES256 або EdDSA (асиметричні схеми)
- Публічний ключ доступний для верифікації від третіх сторін
- Приватний ключ зберігається тільки на сервісі видачі

### 5.5 Відповідність до регуляторних вимог

#### 5.5.1 GDPR (General Data Protection Regulation)

**Вимоги:**
- Мінімізація даних: збирати лише необхідні дані
- Шифрування: персональні дані повинні бути зашифровані
- Право на забування: користувачі можуть вимагати видалення своїх даних
- Прозорість: користувачі повинні знати, які дані збираються

**Як система задовольняє:**
- ✅ Мінімізація: збираються лише вкладення облиця, не сирі біометричні дані
- ✅ Шифрування: всі дані зашифровані AES-256-GCM
- ✅ Аудит: всі дії записуються (без PII)
- ⚠️ Право на забування: потребує реалізації функції видалення користувача

#### 5.5.2 BIOMETRIC INFORMATION PRIVACY

Деякі юрисдикції (BIPA, Illinois) вимагають явної згоди перед збіранням біометричних даних.

**Рекомендації:**
- Явна форма згоди перед реєстрацією
- Зберігання журналу зачинів
- Механізм видалення біометричних даних

### Приклад 1: Повна реєстрація та аутентифікація

```bash
# 1. Створити DID

  -H "Content-Type: application/json" \
  -d '{}' | jq .

# 2. Розпочати реєстрацію
curl -X POST http://localhost:8000/v1/enroll/start \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user@example.com",
    "version": "v1"
  }' | jq .

# 3. Завершити реєстрацію (з вкладенням)
curl -X POST http://localhost:8000/v1/enroll/finish \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user@example.com",
    "template_data": "[0.1, 0.2, ..., 0.128]",  # Base64 embedding
    "salt": "x1y2z3w4",
    "version": "v1",
    "storage_uri": "ipfs://QmXxxx",
    "challenge": "a1b2c3d4e5f6g7h8"
  }' | jq .

# 4. Отримати виклик для аутентифікації
curl -X POST http://localhost:8000/v1/auth/challenge \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user@example.com"}' | jq .

# 5. Верифікувати та отримати VC
curl -X POST http://localhost:8000/v1/auth/verify \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user@example.com",
    "did": "did:key:z6Mk...",
    "nonce": "f1e2d3c4b5a6g7h8",
    "desired_level": 2,
    "template_data": "[...]",
    "wallet_signature": "base64_sig"
  }' | jq .

# 6. Запросити доступ
curl -X POST http://localhost:8000/v1/access/request \
  -H "Content-Type: application/json" \
  -d '{
    "did": "did:key:z6Mk...",
    "resource": "finance",
    "desired_level": 2,
    "factors": ["wallet-sign", "biometric-proof"],
    "vc_jwt": "eyJhbGc...",
    "wallet_signature": "base64_sig"
  }' | jq .
```
