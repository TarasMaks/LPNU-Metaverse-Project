# Біометрична ідентифікація з AI + блокчейном для Web3/метавсесвіту

Цей документ фіксує вимоги, обмеження та архітектурні рішення для системи багатофакторної біометричної ідентифікації із застосуванням AI, блокчейну та DID/VC. Він орієнтований на швидкий PoC із подальшим нарощуванням функціональності.

## 1. Вимоги та обмеження
- Біометрії: обличчя, голос, відбиток, райдужка, поведінкова (жести, хода); допускаються комбінації.
- Сценарії: логін у Web3-сервіси, підпис транзакцій, доступ до просторів/кімнат метавсесвіту, доступ до персональних даних (профіль/фінанси/медицина/KYC).
- Рівні доступу (приклад): L0 гість, L1 базовий профіль, L2 персональні дані, L3 фінансові/чутливі, L4 адмін/власник. Для кожного рівня визначається політика MFA.
- Обмеження: низька затримка для VR/AR, робота при поганому інтернеті/офлайн, приватність (GDPR-подібні вимоги), неможливість «змінити» біометрію після компрометації.
- Безпека даних: сирі біометричні дані ніколи не зберігаються на блокчейні; допускається тільки хеш/комітмент шаблону та посилання на зашифроване сховище з аудитом подій.

## 2. Високорівнева архітектура
- **Client SDK (Unity/Unreal/Web):** захоплення біометрії, локальна перевірка liveness, формування «біометричного доказу», підпис викликів гаманцем.
- **AI Biometric Service:** моделі розпізнавання, liveness, антиспуфінг; видача короткоживучих токенів/атестацій.
- **Policy & Access Gateway:** єдина точка входу до персональних даних; валідація MFA, рівня доступу й політик ризику.
- **Blockchain layer:** DID/VC, смартконтракти для реєстрації ідентичності, політик доступу та аудиту.
- **Off-chain encrypted storage:** IPFS/S3/DB із шифруванням, KMS/ключі; зберігання шаблонів і персональних даних.

## 3. Модель ідентичності: DID + Verifiable Credentials
- DID прив’язаний до адреси гаманця.
- Біометрія виступає фактором для отримання короткоживучої VC/атестації (наприклад, `BiometricVerified level=2 exp=10min`).
- Політики доступу базуються на DID, наборі VC та контексті (ризик, пристрій, гео, час, сума транзакції).
- Що реалізувати: генерація DID або інтеграція з метод-реєстром; випуск/перевірка VC; прив’язка VC до сесії та гаманця для запобігання передачі.

## 4. Біометричний пайплайн
### 4.1 Enrollment
1. Захоплення зразків на клієнті, liveness.
2. Побудова embedding/шаблону на пристрої за можливості.
3. Нормалізація, квантування, застосування cancelable template/захищеного перетворення.
4. Шифрування шаблону, збереження off-chain.
5. Запис на блокчейн лише commitment (`hash(template || salt || version)`), метаданих (алгоритм/версія) та URI сховища без персональних даних.

### 4.2 Authentication
1. Capture + liveness на клієнті.
2. Обчислення embedding і формування запиту на валідацію.
3. Валідація локально (TEE) або на сервері.
4. У разі успіху — короткоживучий біо-токен або VC з рівнем довіри.
5. Далі застосовується MFA-політика для потрібного рівня доступу.

### Критичні вимоги
- Антиспуфінг проти deepfake/rewind/3D-mask обов’язковий для продуктивних сценаріїв.

## 5. MFA та політики доступу
- Рівні політик (приклад):
  - L1: підпис гаманцем (possession).
  - L2: підпис гаманцем + біометрія (possession + inherence).
  - L3: L2 + атестація пристрою (possession + inherence + device).
  - L4: L3 + out-of-band або social recovery.
- Policy engine: правила «ресурс → потрібні фактори», зв’язка рівень доступу → набір факторів.
- Risk-based step-up: посилення MFA при високому ризику (нова локація/пристрій, велика транзакція).

## 6. Смартконтракти (мінімальний набір)
- **IdentityRegistry:** DID ↔ wallet, ротація ключів.
- **BiometricCommitmentRegistry:** зберігання commitment-ів, версій, станів (active/revoked).
- **AccessPolicyRegistry:** хеші політик або URI на версії політик, прив’язка до ресурсів.
- **AuditLog:** події доступу/відмови без персональних даних.
- Рекомендовано стартувати з EVM-сумісної мережі (Polygon/Base/Arbitrum) для PoC.

## 7. Off-chain дані та шифрування
- Зберігати персональні дані та біометричні шаблони тільки зашифрованими.
- Ключі: user-managed або KMS/threshold; другий варіант практичніший для UX.
- Рівні доступу через окремі DEK для класів даних або через атрибутивне шифрування/проксі-перешифрування.

## 8. API контракти між сервісами
- `POST /enroll/start` → challenge + параметри.
- `POST /enroll/finish` → запис commitment, збереження шаблону.
- `POST /auth/challenge` → nonce/challenge.
- `POST /auth/verify` → результат + short-lived token/VC.
- `POST /access/request` → ресурс, бажаний рівень, докази MFA → decision + grant.
- `POST /keys/wrap` → видача wrapped-ключа під політику (якщо є KMS).
- SDK методи для Unity/Unreal: capture, liveness, wallet-sign, submit.

## 9. Тест-план і безпека
- Threat modeling: replay, MITM, підміна пристрою, deepfake, викрадення токенів, компрометація шаблонів, correlation attacks.
- Якість біометрії: FAR/FRR, EER, стійкість до шуму, різне освітлення, VR-гарнітури.
- Навантаження: пікові логіни для метавсесвіту, latency.
- Pen-test: підробка `/auth/verify`, повтор challenge, крадіжка VC, атаки на смартконтракти.
- Ротація: перевидання cancelable template, відкликання старих commitment-ів.

## 10. Поетапна реалізація
1. PoC: підпис гаманцем + face recognition + простий registry контракт + audit events.
2. Додати liveness і антиспуфінг; перейти на «VC замість токена».
3. Додати policy engine з рівнями доступу та step-up MFA.
4. Додати шифрування даних, ключі, gateway для доступу до персональних сервісів.
5. Для метавсесвіту: Unity/Unreal SDK, оптимізація latency, частковий on-device inference.
