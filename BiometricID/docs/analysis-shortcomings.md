# Аналіз недоліків репозиторію: біометрична ідентифікація для Web3/метавсесвіту

Заявлена мета: *методи біометричної ідентифікації з використанням алгоритмів штучного інтелекту та технології блокчейн дадуть змогу користувачам підвищити рівень безпеки при використанні персоналізованих інформаційних сервісів у системах Web 3.0 та метавсесвіті, шляхом використання мультифакторної аутентифікації з кількома рівнями доступу до персональних даних.*

Нижче наведено порівняння проєктного документа (`docs/biometric-identity-design.md`) із фактичною реалізацією (~584 рядків Python-коду).

---

## 1. Блокчейн — повністю відсутній в імплементації

Проєктний документ визначає чотири смартконтракти:
- `IdentityRegistry` (DID ↔ wallet, ротація ключів)
- `BiometricCommitmentRegistry` (збереження commitment-ів шаблонів, статуси, revocation)
- `AccessPolicyRegistry` (хеші політик, прив'язка до ресурсів)
- `AuditLog` (події доступу без персональних даних)

**Фактичний стан:** нульова реалізація. Немає Solidity-коду, web3-бібліотек, ABI контрактів чи будь-якої взаємодії з блокчейном. Модуль `did.py` (`app/did.py:6-8`) генерує випадковий рядок у форматі `did:example:<random_hex>` — він не реєструється в жодному DID-методі, не має on-chain прив'язки й не підписаний криптографічно.

Commitment, обчислений при enrollment (`models.py:93-94`), повертається клієнту, але ніде не зберігається, крім in-memory Python-словника. Немає механізму верифікації через ledger.

**Вплив:** частина тези про «блокчейн» є виключно архітектурною проєкцією без виконуваного доказу.

## 2. AI / біометрична верифікація — поверхнева інтеграція

Проєктний документ обіцяє: розпізнавання обличчя, голосу, відбитків пальців, райдужки та поведінкову біометрію (жести, хода), з AI-liveness та anti-spoofing.

**Фактичний стан:**
- Тонка обгортка навколо DeepFace (`app/deepface_adapter.py`), що викликає `DeepFace.verify()` з `enforce_detection=False` (рядок 41) — система приймає зображення навіть без виявленого обличчя, що є навмисним послабленням безпеки.
- **Liveness-детекція відсутня** — критична вимога з розділів 4.1, 4.2 проєктного документа.
- **Anti-spoofing відсутній** — система прийме фото з фото, роздрукований знімок або кадр deepfake-відео.
- **Голос, відбитки, райдужка, поведінкова біометрія** — не реалізовані; тільки обличчя через сторонню бібліотеку.
- **Захист шаблонів відсутній** — проєктний документ вказує cancelable templates та захищені перетворення (розділ 4.1, крок 3), але код просто хешує рядок `template_data`.
- Endpoint `/biometric/face/verify` повністю відключений від потоку enrollment/authentication. Це ізольований endpoint, який ніде не використовується в pipeline автентифікації.

**Вплив:** AI-компонент — це виклик чужої бібліотеки без інтеграції в потік автентифікації та без захисних біометричних механізмів.

## 3. Потік автентифікації — фактична біометрична верифікація відсутня

Це критичний структурний недолік. Endpoint `/auth/verify` (`main.py:162-174`) виконує:
1. Перевірку збігу nonce
2. Перевірку існування запису шаблону
3. Видачу VC

**Біометричні дані ніколи не порівнюються.** Перевірка nonce — це механізм захисту від replay, а не біометричний порівняльний аналіз. Немає виклику `verify_face()` чи іншого біометричного порівняння під час автентифікації. Будь-який клієнт, що знає nonce, отримує VC безумовно.

Аналогічно, `/enroll/finish` (`main.py:135-149`) приймає рядок `template_data`, хешує його та зберігає хеш. Код ніколи не перевіряє, чи є ці дані справжнім біометричним шаблоном, а тим більше — чи походять вони від реальної особи.

**Вплив:** автентифікація — це перевірка nonce challenge-response, що видає себе за біометричну верифікацію. Зловмисник із nonce отримує повний доступ.

## 4. Вразливості безпеки

| Проблема | Розташування | Опис |
|---|---|---|
| **Відсутнє обмеження частоти запитів** | Всі endpoints | Brute-force атаки на challenges/nonce нічим не обмежені |
| **Відсутня санітизація шляхів до файлів** | `main.py:99-100`, `deepface_adapter.py:26-27` | `img1_path`/`img2_path` передаються безпосередньо в `DeepFace.verify()` — ризик path traversal; зловмисник може читати довільні файли сервера |
| **HTTPS не примусовий** | `main.py` | Біометричні дані та credentials передаються відкритим текстом |
| **API не захищений автентифікацією** | Всі endpoints | Будь-який клієнт може реєструвати, автентифікувати або запитувати доступ для будь-якого користувача |
| **Challenge/nonce без терміну дії** | `models.py:23-33` | `EnrollmentChallenge` та `AuthChallenge` зберігають `created_at`, але це поле ніколи не перевіряється — challenges дійсні нескінченно |
| **Одноразовий nonce не видаляється** | `main.py:164-166` | Після верифікації auth challenge залишається у store — можливий replay |
| **Enrollment challenge не видаляється** | `main.py:137-138` | Після завершення enrollment challenge залишається придатним до повторного використання |
| **VC без криптографічного підпису** | `models.py:46-53` | `VerifiableCredential` — звичайний dataclass без цифрового підпису, proof чи issuer. Не відповідає W3C VC Data Model |
| **Глобальний змінний стан** | `main.py:22` | `store = InMemoryStore()` на рівні модуля — конкурентні запити спричиняють race conditions |
| **CORS не налаштований** | `main.py` | Веб-клієнти та клієнти метавсесвіту/браузера не зможуть використовувати API |

## 5. MFA Policy Engine — надмірно спрощений

Policy engine (`app/policy.py`) — статичний словник із 4 рівнів.

- **Відсутня прив'язка ресурс→політика** — проєктний документ визначає «ресурс → потрібні фактори», але код ігнорує поле `resource` (`main.py:187`). Запит до `"finance"` та `"public-profile"` обробляється однаково.
- **Валідація факторів базується на довірі** — клієнт самостійно повідомляє свої фактори як рядки (`["wallet-sign", "biometric-proof"]`). Сервер не верифікує жоден із них: немає перевірки підпису гаманця, біометричного доказу, атестації пристрою.
- **Risk step-up наївний** — `step_up_if_risky()` (`policy.py:62-68`) додає `len(risk_indicators)` до рівня. Індикатори ризику — це рядки від клієнта без серверної оцінки. Клієнт може просто не надсилати їх.
- **Немає динамічного управління політиками** — політики зашиті в код, не конфігуруються для ресурсів чи організацій.

## 6. Збереження даних — тільки in-memory

Весь стан зберігається в `InMemoryStore` (`models.py:71-90`):
- Дані втрачаються при перезапуску сервера
- Немає бази даних, файлового збереження, Redis чи блокчейн-сховища
- Тести маніпулюють глобальним об'єктом store напряму (`tests/test_app.py:8-13`), створюючи спільний змінний стан
- Немає шляху міграції до реальної БД (відсутні ORM, repository pattern)

## 8. Тестування — мінімальне покриття

- Лише **3 тестових функції** для всієї системи
- Немає unit-тестів для окремих модулів (`models.py`, `policy.py`, `did.py`)
- Немає негативних/граничних тестів (прострочений VC, невірний користувач, дублювання enrollment, невалідні template_data, конкурентні запити)
- Немає тестів безпеки (path traversal, injection, replay-атаки)
- Немає тестів продуктивності/навантаження (актуально для вимог latency метавсесвіту)
- Тести використовують глобальний стан через модульний об'єкт `store` — ізоляція тестів залежить від ручного виклику `reset_store()`
- Немає CI/CD конфігурації (GitHub Actions, `tox.ini`, `Makefile`)

## 9. Проблеми архітектури коду

- **Відсутній поділ відповідальностей на API-рівні** — `main.py` змішує DTO запитів/відповідей, обробники endpoints та оркестрацію в одному файлі на 224 рядки
- **Відсутня ін'єкція залежностей** — глобальний `store` імпортується та змінюється напряму
- **Відсутнє логування** — жодного використання модуля `logging`; неможливо дебажити чи аудитувати
- **Відсутнє управління конфігурацією** — немає `.env`, файлу налаштувань, читання змінних середовища; TTL (600с), DID-метод ("example"), назви моделей зашиті в код
- **Відсутня стратегія обробки помилок** — тільки `HTTPException` з загальними кодами; немає структурованих відповідей про помилки
- **Відсутнє версіонування API** — endpoints без префіксу версії (`/v1/...`)
- **Відсутній Dockerfile або конфігурація деплойменту** — немає шляху до продуктивного запуску

## 10. Розрив між теорією та реалізацією

Проєктний документ є комплексним і добре структурованим, покриваючи threat modeling, метрики FAR/FRR, плани pen-testing та поетапний roadmap. Однак PoC ледве реалізує Фазу 1 власного roadmap:

- **Ціль Фази 1:** «підпис гаманцем + face recognition + простий registry контракт + audit events»
- **Фактичний стан:** бібліотека face recognition імпортована, але не під'єднана до потоку auth; підпис гаманця відсутній; registry контракт відсутній; audit events відсутні

Кодова база — це REST API-скелет із placeholder-логікою. Фундаментальна теза — що AI + блокчейн біометрична ідентифікація підвищує безпеку — не може бути продемонстрована чи валідована поточним кодом, оскільки:
1. Біометричні дані фактично не верифікуються під час автентифікації
2. Блокчейн нічого не записує
3. Вихід AI-моделі не впливає на рішення про доступ
4. Фактори безпеки самодекларуються ненадійними клієнтами
