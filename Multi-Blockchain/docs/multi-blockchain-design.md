# Інтеграція приватних та публічних блокчейн-інфраструктур

Модель інтеграції приватних та публічних блокчейн-інфраструктур у децентралізованій територіально-розподіленій інформаційній системі для адаптивного оброблення транзакцій та смарт-контрактів. Цей документ описує архітектурні рішення, рівні системи та ключові компоненти.

## 1. Архітектурний принцип

Система реалізує стратегічний принцип розподілу відповідальності для розв'язання фундаментального конфлікту між безпекою та пропускною здатністю. Замість обробки всіх операцій в одному ланцюжку, транзакції диференціюються за критичністю і обробляються на двох рівнях:

- **Рівень розрахунків (Settlement Layer / L1):** Ethereum 2.0 з Proof-of-Stake. Критичні зміни стану — первинна реєстрація права власності, юридично значущі передачі активів. Механізм slashing робить атаку 51% економічно недоцільною.
- **Рівень виконання (Execution Layer / L2):** Layer-2 рішення для високонавантажених операційних даних — логи моніторингу, сенсорні потоки, проміжні звіти. Пріоритет: низька затримка та висока швидкість.

## 2. Криптографічні зв'язки між рівнями

Зв'язок між рівнями реалізується через періодичне якоріння (anchoring) кореневих хешів стану L2 в основному ланцюжку L1. Це дозволяє:
- Автоматично обробляти дані з низьким ризиком на L2.
- Зберігати цілісний підсумок в основному захищеному блокчейні.
- Верифікувати будь-яку L2 транзакцію проти L1 стану.

## 3. Модуль адаптивної маршрутизації

Центральний інтелектуальний компонент — модуль політик та адаптивної маршрутизації. Оцінює параметри транзакції за зваженою моделлю та визначає цільове середовище:

### Критерії маршрутизації:
- **Цілісність та невідворотність** (вага 0.30): вимоги до integrity гарантують обробку на L1.
- **Затримка та обсяг даних** (ваги 0.15 + 0.15): великі дані та низька допустима затримка направляються на L2.
- **Юридичний ризик** (вага 0.25): висока ймовірність суперечок — маршрутизація на L1.
- **Конфіденційність** (вага 0.15): обмеження доступу — обробка відповідно до політики.

### Жорсткі правила:
- `critical` → завжди Settlement Layer.
- `low` → завжди Execution Layer.
- `standard` → зважена оцінка, поріг ≥ 0.50 → L1, інакше L2.

## 4. Канонічна ідентичність (PUF + NFT)

Механізм використання PUF (Physically Unclonable Functions) на основі біометричної аутентифікації:
- PUF-відповідь хешується через HMAC-SHA256 з сіллю → commitment.
- Commitment визначає DID (`did:puf:<hash>`).
- NFT на основі ERC-721/1155 мінтиться на Settlement Layer.
- Канонічна ідентичність: незмінний зв'язок суб'єкт ↔ цифровий двійник.

## 5. Гібридне зберігання (IPFS)

Модель зберігання на основі IPFS (InterPlanetary File System):
- Великі масиви (3D-моделі, тензори) зберігаються поза мережею.
- В блокчейні фіксується тільки Content Identifier (CID).
- Забезпечується незмінність даних при мінімальних витратах on-chain.
- Локальний fallback-стор для розробки та тестування.

## 6. Middleware-стек

Спеціалізований Middleware з балансувальником навантаження:
- Round-robin розподіл RPC-запитів між вузлами.
- Автоматичне виключення нездорових ендпоінтів.
- Retry з failover для високої доступності.
- Прийнятна обчислювальна складність для мільйонів користувачів.

## 7. Подійно-орієнтована синхронізація

Синхронізація через веб-хуки (Alchemy Notify):
- Вхідні сповіщення про зміну стану блокчейну.
- Диспетчеризація до зареєстрованих обробників.
- Миттєве оновлення користувацьких інтерфейсів.
- Аутентифікація через токен для захисту від підроблених подій.

## 8. Смарт-контракти

### SettlementAnchor.sol
Якоріння L2 кореневих хешів стану на L1. Верифікація, відкликання.

### CanonicalIdentityNFT.sol
ERC-721 токен канонічної ідентичності. PUF commitment, метадані, мінт/верифікація/відкликання.

### TransactionRegistry.sol
Реєстр критичних транзакцій на Settlement Layer. Хеші payload, аудит.

## 9. API контракти

| Ендпоінт | Опис |
|---|---|
| `GET /health` | Стан сервісу та підключених компонентів |
| `POST /v1/transaction/submit` | Подання транзакції з адаптивною маршрутизацією |
| `GET /v1/transaction/status/{tx_id}` | Статус транзакції |
| `POST /v1/identity/register` | Реєстрація канонічної ідентичності (PUF + NFT) |
| `POST /v1/identity/verify` | Верифікація PUF-відповіді |
| `POST /v1/storage/pin` | Закріплення даних в IPFS + якоріння CID |
| `POST /v1/storage/resolve` | Отримання даних за CID |
| `POST /v1/anchor/submit` | Якоріння L2 state root на L1 |
| `POST /v1/anchor/verify` | Верифікація якоря на L1 |
| `POST /v1/webhook/notify` | Отримання подій від моніторингу ланцюга |

## 10. Поетапна реалізація

1. **PoC:** Адаптивна маршрутизація + канонічна ідентичність (PUF) + IPFS зберігання + базові контракти.
2. **Інтеграція L1/L2:** Підключення до реальних Ethereum та L2 провайдерів, автоматичне якоріння.
3. **Масштабування:** Middleware-стек з балансувальником навантаження, оптимізація RPC.
4. **Продуктивне середовище:** Подійно-орієнтована синхронізація, Alchemy Notify, повний аудит.
5. **Метавсесвіт:** Інтеграція з BiometricID, Unity/Unreal SDK, оптимізація latency.
